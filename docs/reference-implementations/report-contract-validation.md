# Report Contract Validation

Implementation status as of 2026-06-18: implemented as a CineJelly-owned no-spend Node.js report/schema validator, JSON schema, package command, and operator documentation. This Reference Implementation is documentation-only and must not import or execute upstream snapshot code.

## Purpose

CineJelly has many release and business-readiness reports. Operators need a single local check that catches schema drift before a report is used as release evidence or handed to a customer/operator.

## Rules

1. The validator must not call Atlas, stock provider APIs, deployment endpoints, source-video URLs, FFmpeg, render routes, or billing/payment APIs.
2. The validator must not read `.env` or expose provider keys, bearer tokens, signed URLs, customer media, or local-only artifact paths.
3. The validator validates schema shape plus explicitly documented report-local semantic invariants; it must not turn blocked business evidence into a pass.
4. Default report contracts are skipped only when a report file is absent; custom `--contract` and `--only-contract` inputs are required.
5. The validator should support the local schema features used by CineJelly reports: `type`, `required`, `properties`, `additionalProperties`, `items`, `enum`, `const`, min/max constraints, string patterns, `date-time`/`uri` formats, local `$ref`, `allOf`, `anyOf`, `oneOf`, `not`, and basic `if`/`then`.
6. `--allow-launch-doctor-in-progress` is reserved for the commercial launch doctor while it rewrites its own report across multiple contract-refresh passes; default report-contract validation must remain strict for completed launch-doctor reports.

## Acceptance Checks

- `node scripts/validate-report-contracts.mjs` reports `status: pass` for the current release-candidate report set.
- The generated report says schema-shape pass is not customer-traffic approval.
- Existing blocked reports can pass schema validation while still preserving their blocked/fail business status.
- Report redaction still removes string secrets but preserves boolean readiness fields such as `apiKeyConfigured`.
- When `atlas-billing-generated-audio-smoke-report.json` exists, report-contract validation includes it against the Atlas billing readiness schema.
- When deployment-readiness capture reports exist, report-contract validation includes them and catches missing `atlasCloudDocsConformanceStatus` summary evidence.
- When `snapshot-parity-audit-report.json` exists, report-contract validation includes it and catches schema drift in subtree/source-lineage/import-boundary guardrail evidence.
- When `snapshot-parity-audit-report.json` exists, report-contract validation also requires all configured snapshot guardrails to pass and keeps `canClaimFullSnapshotParity=false` plus `canReleaseToCustomerTraffic=false`.
- When `director-style-semantic-review.json`, `director-style-audio-review.json`, `director-style-runtime-review.json`, or `director-style-governance-review.json` exists, report-contract validation checks the structured review input schema before the quality benchmark consumes it.
- When `director-style-review-drafts-report.json` exists, report-contract validation confirms the generator was no-spend/no-network, the artifact binding is explicit, every draft stays `needs_review`, and the report keeps `canUseDraftsAsAcceptedReviewEvidence=false` plus `canClaimDirectorBenchParity=false`.
- When `director-style-review-evidence-readiness-report.json` exists, report-contract validation confirms the validator was no-spend/no-network, summary counts match review rows, accepted-review flags are true only on `status=pass`, and `canClaimDirectorBenchParity=false` plus `canReleaseToCustomerTraffic=false` remain enforced.
- When `director-style-review-evidence-guard-smoke-report.json` exists, report-contract validation confirms the review-evidence guard accepted a clean artifact-bound review bundle, rejected an unsafe accepted-looking semantic packet with schema/redaction failure, kept accepted-review/parity/customer-release claims false, and did not echo raw unsafe URL/token text in public output.
- When `director-style-benchmark-report.json` exists, report-contract validation includes the artifact-contract benchmark schema, verifies it still reports `canClaimDirectorBenchParity=false`, validates `parityEvidenceMatrix` counts, unique requirement ids, and met/missing evidence consistency, requires semantic/audio/runtime/governance review rows to be `met` only when accepted structured review evidence is bound to the paid-render project/request/deliverable fingerprint, requires the generated-audio provider row to be `met` only when the generated-audio validation report has passed every provider/billing/schema/output/manual-review gate, requires long-form duration/manual-review rows to be `met` only with measured 2-8 minute duration or accepted long-form validation evidence, and requires the license/runtime permission row to be `met` only when the structured governance review has accepted all required checks and binding.
- When `commercial-launch-inputs-report.json` exists, report-contract validation requires `commandPlanAudit.status` to be `pass` with no command-plan issues and requires both the live provider action evidence input/command and graph-resume enqueue evidence input/command to be present.
- When release-audit checks include redacted findings, the schema accepts only primitive finding fields and still rejects unrelated report drift.
- When `commercial-launch-doctor-report.json` exists, report-contract validation requires the core launch-doctor command sequence, refreshed quality benchmark evidence, refreshed review-evidence guard smoke, final report-contract pass, provider handoff/resume-state smoke pass/warn statuses when enabled, and explicit skipped provider statuses when `--skip-provider-handoff-smokes` is used.
- When launch doctor calls report-contract validation before its final command has been appended, it must pass `--allow-launch-doctor-in-progress`; a normal standalone `validation:report-contracts` run must still reject incomplete final launch-doctor evidence.
- When `business-completion-audit-report.json` exists, report-contract validation requires blocker summaries, product-code gap summaries, snapshot/report/release status booleans, ready paid-gate counts, and release flags to match the source arrays and readiness snapshot.
- When `business-readiness-report.json` exists, report-contract validation requires `status`, `completion`, `canRunAdditionalPaidValidation`, `canRunLongFormValidation`, `readyPaidGateCount`, `canReleaseToCustomerTraffic`, and `releaseBlocker` to match the underlying check statuses and weights.
- When `business-readiness-validation-plan.json` exists, report-contract validation requires the generated-audio, long-form, full paid-sequence, and source-video paid-slice rows to exist exactly once; their budget statuses must match the report cost plan, and full-sequence readiness must stay false when cost estimates are incomplete or over budget.
- When `render-provider-handoff-action-ledger-report.json` exists, report-contract validation requires apply and execution summaries to match their underlying result objects, keeps `providerCallsMade=false`, keeps every distributed-resume claim false, and rejects pass reports with failed checks.
- When `production-graph-resume-state-report.json` exists, report-contract validation requires no-spend/no-network/no-provider/no-external-queue evidence, graph/provider summary counts to match the capsule, local queue enqueue/replay/lease/ack lifecycle to complete, action-ledger prediction-ID dependency to remain true, raw graph/provider/output URL/local path/secret/raw prediction-ID/raw queue-name/raw worker-ID leakage to stay absent, and every distributed-resume/customer-release claim to remain false.
- When `production-graph-resume-queue-service-smoke-report.json` exists, report-contract validation requires protected local HTTP queue-service evidence, enqueue/replay/lease/lease-mismatch/ack lifecycle completion, preflight queue-path readiness, raw queue-name/worker-ID/deployment-token leakage to stay absent, and `canClaimDistributedResume=false`.
- When `render-provider-graph-resume-worker-smoke-report.json` exists, report-contract validation requires a no-spend local HTTP worker bridge report, one first-run `resume_polling` enqueue, one second-run replay, skipped non-resume actions, one digest-only queue record, no real provider calls, false live-evidence/distributed-resume claims, and no raw queue name, prediction ID, token, URL, or local path leakage.
- When `render-provider-production-handoff-report.json` exists, report-contract validation requires no provider/render calls, complete acquire/held/heartbeat/release/post-release/list/active operations, summary counts matching operations, deployment host redaction, a SHA-256 deployment base URL fingerprint, no raw lease `jobId` fields in public operation responses, usable-evidence flags only for pass deployment captures, and false distributed-resume/customer-release claims.
- When `render-provider-live-action-evidence-draft-report.json` exists, report-contract validation requires the helper to be no-spend/no-network, the template to stay template-only and rejected by the real evidence schema if copied directly, and every live-action, graph-resume, distributed-resume, and customer-release claim to remain false.
- When `render-provider-live-actions-report.json` exists, report-contract validation requires the validator to be no-spend/no-network, requires summary counts to match execution evidence including same-entry `resume_polling` + `graph_resume_enqueue` + `resume_enqueued` graph-resume evidence counts, rejects inconsistent action/providerCallKind/resultStatus combinations, rejects pass reports without `--confirm-live-provider-actions`, matching production-handoff deployment fingerprint, passing production handoff evidence, provider-call evidence, resume-polling evidence, terminal-close/manual-audit evidence, or full redaction review, only lets the distributed-resume evidence slice become usable when valid graph-resume evidence exists, and still keeps `canClaimDistributedResume=false`.

- When `render-provider-graph-resume-enqueues-report.json` exists, report-contract validation requires the validator to be no-spend/no-network/no-queue, requires summary counts to match enqueue rows, rejects pass reports without `--confirm-graph-resume-enqueues`, passing/usable live action graph-resume evidence, deployment fingerprint binding, action/job matches, full redaction review, and digest-only payload storage, and still keeps `canUseAsDistributedResumeEvidence=false`, `canClaimDistributedResume=false`, and `canReleaseToCustomerTraffic=false`.
